# SmartIV setup and deployment guide

This project has two parts that work together:

- **Website and API:** React dashboard plus the Node/Express server.
- **Hardware:** one ESP32, two HX711 load-cell readers, and two IV bags. Channel 1 reports Bed 1; channel 2 reports Bed 2.

GitHub stores the source code. The full application needs a running Node server as well, so this guide uses Render to build and run the app from the GitHub repository. GitHub Pages alone cannot run the API, SQLite database, login, or live ESP32 readings.

## A. Connect the ESP32 to your local website

### 1. Start the API in hardware mode

In `server/.env`, set:

```dotenv
SIMULATE=false
```

Start the API from a PowerShell terminal:

```powershell
cd C:\Users\Janani\smartiv\server
npm run dev
```

The API listens on port `3001`. Keep this terminal running. The website can keep running on `http://localhost:5173` in its own terminal.

### 2. Create the private firmware configuration

From the project root, copy the example:

```powershell
Copy-Item firmware\smartiv_esp32\config.h.example firmware\smartiv_esp32\config.h
```

Edit `firmware/smartiv_esp32/config.h`. Fill in the Wi-Fi SSID and password, then set:

```cpp
#define API_HOST "192.168.1.4"
#define API_PORT 3001
#define API_PATH "/api/readings"
#define API_USE_TLS 0
#define UNIT_LABEL "IVU-01"
#define BED_FOR_CHANNEL_1 1
#define BED_FOR_CHANNEL_2 2
```

`192.168.1.4` is this computer's current Wi-Fi address; confirm it with `ipconfig` before uploading. If it changes, update `API_HOST`. Use the computer's LAN IP, **not** `localhost`: on the ESP32, `localhost` would mean the ESP32 itself. The ESP32 and computer must be on the same Wi-Fi network. Guest Wi-Fi can block devices from reaching each other.

From a phone on that same Wi-Fi, open `http://192.168.1.4:3001/api/health`. It should return JSON. If it does not, allow inbound TCP port `3001` through Windows Firewall and check that the API terminal is still running. The ESP32 talks to port `3001`; the browser uses port `5173`.

### 3. Set the device key

Set `SMARTIV_DEVICE_KEY` in `config.h` to the key for `IVU-01`. The server keeps only a hash, so it cannot recover a key that was lost. The first database seed prints the key once. Use that saved value if you have it; otherwise the unit key must be reissued before the board can authenticate.

Keep `config.h` private. It contains the Wi-Fi password and device key, and `.gitignore` excludes it from Git.

### 4. Calibrate and upload

Install the Arduino IDE libraries **ArduinoJson** and **HX711**. Measure the empty bag and tubing weight for each channel, then calibrate each load cell with a known weight. Set the corresponding `EMPTY_BAG_MASS_G_CHANNEL_n` and `CALIBRATION_FACTOR_CHANNEL_n` values in `config.h`; the example factors are placeholders. Do not rely on displayed volumes until calibration is checked against known weights.

Open `firmware/smartiv_esp32/smartiv_esp32.ino`, select the ESP32 board and serial port, upload, and open Serial Monitor at `115200` baud. The board reports both channels every two seconds. Sign in to the site as a nurse assigned to Beds 1 and 2 or as the ward admin; incoming readings should update the cards live. A bed stays **Offline** until its unit reports.

## B. Deploy the full app from GitHub

### 1. Push the project to GitHub

The configured repository is `https://github.com/jananiravindran07/smartiv`. Review the files before pushing. From PowerShell in the repository root:

```powershell
git status
git add -A
git commit -m "Prepare SmartIV deployment"
git push origin main
```

The local `.env`, SQLite database, and firmware `config.h` are ignored by Git. Confirm they do not appear in `git status` before committing.

### 2. Create the Render service

1. Sign in to Render and choose **New → Blueprint**.
2. Connect GitHub and select `jananiravindran07/smartiv`.
3. Review the resources described by `render.yaml`, then apply the Blueprint.
4. When prompted for `SEED_DEMO_PASSWORD`, choose a new, unique password with at least 12 characters. Do not reuse the local demo password.
5. Wait for the first deploy to finish. Render builds the frontend, migrates the SQLite database, and seeds the initial demo ward. `JWT_SECRET` is generated by Render.

The Blueprint attaches a persistent disk at `/var/data` for SQLite. Render requires a paid web-service plan for persistent disks; without persistent storage, the ward database would be lost on a restart or deploy. This deployment starts with a fresh seeded database; it does not copy the local `server/data` file.

### 3. Check the deployment and sign in

Open the service URL shown by Render, then visit `<service-url>/api/health`. The response should contain `"ok":true` and `"simulate":false`. Sign in with the admin staff ID `A-1001` and the password you set as `SEED_DEMO_PASSWORD`.

On the first deployment, the seed command prints the new cloud device key once in the Render service logs. Save it as a secret for the ESP32; a local device key will not authenticate against the cloud database.

### 4. Point the ESP32 at the deployed service

In `config.h`, use the Render hostname without a scheme, for example `smartiv-ward.onrender.com`, set `API_PORT` to `443`, keep `API_PATH` as `/api/readings`, and set `API_USE_TLS` to `1`. Put the Render service's trusted root CA certificate in `ROOT_CA_PEM`, then add the cloud device key from the first seed log. The firmware validates the HTTPS certificate; do not disable that validation for an internet deployment.

Upload the sketch again. Once the unit is online, the hosted dashboard should show live readings for Beds 1 and 2 and demo data for the other beds.

## Future updates

Render watches the configured GitHub branch and deploys new commits automatically. Review each change before pushing it to `main`, since a push can update the live ward service.
